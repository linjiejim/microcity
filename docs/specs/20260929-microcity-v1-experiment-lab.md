# MicroCity v1：社会实验室

- 日期：2026-09-29
- 状态：done（2026-09-29 本地落地并验证；用户授权“按建议继续推进深化、不用逐项确认”，本文未逐条审阅）
- 依赖：[v0 停电闭环](20260929-microcity-v0-outage-loop.md)（内核、服务端、前端、D1–D19 全部沿用）
- 范围：信息架构重排；信任随经历演化与多轮事件；按模板规则生成小镇并支持对话建镇；复盘工作区（反应墙、社会演化、轨迹、报告）；多 seed 实验；v0 遗留缺口
- 明确不做：120 人、完整 72 类动作、邻里群聊渠道、居民采访、社交信息流、登录与部署

## 1. 背景与目标

v0 证明了“为什么知道、为什么这样选”可以逐步追溯。用户试用后提出三点：

1. 同屏信息太多：城市、居民列表、社会看板、五车道时间轴、模型健康度挤在一起。
2. 想要“社会实验”的感觉：
   - 一条消息发出去后，先看每个人的反应；
   - 过一段时间，再看每个人的状态和想法变了没有、社会形态有没有变化；
   - 规则设定好之后，观察社区在条件和约束下往哪个方向演化；
   - 最后由 LLM 总结实验结果。
3. 建镇要能用对话完成：LLM 按预设的模板规则搭出小镇、居民和设施，让实验设计更灵活。

另外，v0 评估里留下的缺口也一并处理：单 seed 结论不稳；“有意但受阻”这个漏斗状态从未被触发；“不用电”标签会延续到停电时段之外；关系是静态的。

v1 的立项标准：

> 选一个小镇（或者用对话造一个），设定规则和事件，跑起来；消息发出后能逐人看到反应，过一段时间能看到每个人的想法和社会结构变了什么，最后得到一份每个数字都可追溯的实验报告。

## 2. 设计

### 2.1 信息架构：三个工作区

顶栏的工作区切换是一级导航，每个工作区只回答一个问题。

| 工作区 | 回答的问题 | 主要内容 |
| --- | --- | --- |
| 设计 | 做一个什么样的实验？ | 对话建镇 + 模板；预览（像素小地图、人口与媒介画像、剧本时间线）；开始观察 / 设计对照实验 |
| 观察 | 现在发生了什么？ | 城市占满中央；右侧是「现场 · 居民 · 新闻」三个标签；底部“章节条”标出关键时刻 |
| 复盘 | 结果怎样？为什么？ | 时间刷 + 对比基准；「反应墙 · 社会 · 对照 · 报告」四个标签 |

观察工作区相对 v0 做了减法：

- 社会看板（漏斗、时段普查、后果）移到复盘的「社会」标签。
- 模型健康度和重放校验移进顶栏的“诊断”弹窗。
- 默认右栏是“现场”：把事件流合成一行一句的叙事，例如“10:12 马芳把‘下午’说成了‘一整天’”。
- 选中居民后显示精简的人物卡（此刻、想法、相信什么、最近的决定）。原来六个标签的完整档案改为按需打开的抽屉。
- 时间轴默认是章节条（关键时刻 + 日刻度），五车道明细作为“明细”开关保留。
- 居民筛选从六个按钮收进一个下拉框。

### 2.2 内核：去掉写死的地点，事件剧本化

地点改为按类型查询。`TownMap` 新增以下方法：

- `placesOfKind`
- `nearestOf(kind, from, {district?, avoid?})`：按门到门步行时间排序，同距离按 id，保证确定性
- `districtBounds`：河道行由地图推出，不再写死 `y ≤ 15`

以下几处原来写死了 W03、P01、W06、W09 这些 id，全部改成“离这里最近的某类地点”：

- 午饭、休闲、买菜、上课、找工作、晨练去哪；
- 替代地点、充电宝商店；
- 调整营业方式：咖啡馆改冷饮，工作室整队搬去图书馆，其他店暂停营业；
- 停电时的公园回退；
- 周末营业流入。

剧本改为由事件规格生成：

```ts
OutageEventSpec {
  id: string;                  // 'E1'
  family?: string; ids?: { notice?: string; clarify?: string; workOrder?: string };  // 经典场景保留 F_OUTAGE / N001 / N002 / WO01
  area: 'north' | 'south'; day: number; from: number; to: number;   // 真实停电（当天秒数）
  notice: { at: SimTime; channels: PublishChannel[]; headline: 'exact' | 'coarse' | 'none'; advice: Advice[] } | null;
  clarify: { at: SimTime; channels: PublishChannel[] } | null;
  workOrder: boolean;
}
```

- `scriptFromEvents(events, map, orgs)` 生成通知、澄清、工单与断电/来电。标题与正文按区域内的地点名和清晰度模板生成。
- `ScenarioDef.outages` 记录世界真相 `{id, family, area, day, from, to}`，以此归属不便、结算过度调整、裁决信任。
- 经典场景的 E1 生成的 `N001` / `WO01` 与 v0 逐字相同，v0 的行为保持不变。
- 多轮事件（例如 D03 通知 → D04 北区停电 → D05 通知 → D06 南区停电）靠同一套机制实现。
- 分支 = 对事件规格打补丁（改渠道、改标题清晰度、加减澄清），再重新生成剧本，替换分叉点之后的脚本。它取代 v0 的 `branchScript(N001/N002)`。

### 2.3 信任随经历演化（社会形态会变）

- 居民新增 `trustGov`（初值 = 特质 `trustOfficial`）和 `trustIn: Record<居民, number>`（有向，缺省回落到关系的 `trust`）。
- 可信度计算改用这两个动态值。在信任变化之前，v0 的所有行为不变。
- 结算时机：一次停电来电时（真相已被看见），对该事件关联的主张族结算。
- 结算对象：见证者，即住在或工作在受影响区域，或当天在该区域、该时段有安排的人。
- 结算写成事件 `trust_changed {agent, target: 'gov' | 居民, from, to, reason, outage, family}`，前端 reducer 同构重建。规则版本 `social_v1`：

| 情形 | 调整 |
| --- | --- |
| 措手不及，且从没从官方渠道接触过通知 | 对政府 −0.12（“停电前没收到任何通知”） |
| 措手不及，但接触过官方通知（只看了标题 / 没当回事） | 对政府 −0.04 |
| 信念来自官方正文，事先做了安排且没被打个措手不及 | 对政府 +0.04 |
| 信念来自官方的“下午”这类粗略标题，并且过度调整 | 对政府 −0.05（“通知只说下午，白白挪了一下午”） |
| 看到过官方澄清 | 对政府 +0.03 |
| 从某人那听到的版本：精确且正确 / 粗略但一致 / “全天” / 地点或日期错 | 对此人 +0.05 / +0.02 / −0.12 / −0.08 |

- 取值夹在 [0.05, 0.95]。
- 不是见证者的人不更新。例如住南区、只听说“北区停一整天”的人，永远不知道真相，这是刻意保留的。
- 第二轮通知的传播因此会受第一轮影响，这正是“社会形态”变化的可观测后果。

### 2.4 v0 缺口

- **有意但受阻**：以下三种情况记 `funnel_stop: blocked`，并写明原因。
  - 选中的改安排在提交时已不合法；
  - 按决定改后的安排因没开门、满员、卖完、钱不够而落空；
  - 自己的安排受影响，但所有改法都被规则排除，例如“岗位在店里，个人无权调整”。原来这种情况记为“与己无关”，是错的。
- **“不用电”标签**：`adapt` 只替换所信的停电时段，前后两段保留原安排。过度调整因此按实际挪动的分钟计。
- **按事件统计后果**：`inconvenience` / `overreaction` 事件带 `outage` id，`stats.byOutage` 分事件累计，指标可以按轮次看。

### 2.5 按模板生成小镇

新增 `TownSpec`，是给人和 LLM 填的声明式规格：

```ts
TownSpec {
  v: 1; name: string; base: 'classic' | 'generated'; seed: number;
  population: { size: 12–60; seniors: 0–0.6; youth: 0–0.6; northShare: 0.2–0.8 };      // generated 时生效
  facilities: { cafe, restaurant, convenience, supermarket, studio, clinic, library, newsroom: 0–3; parks: 1–3 };
  culture: { trustGov, anxiety, sociability, detail: 0.05–0.95 };   // 人群均值；classic 时按差值平移
  media: { push: 0–1; website: 0–1; boards: 0–3 };                  // 订阅推送 / 常看网站的人口比例、公告栏个数
  network: { friends: 0–6; crossDistrict: 0–1; kin: 0–1 };          // 人均朋友数、跨区比例、跨户亲属比例
  characters: CharacterSpec[];                                       // 具名人物（姓名/年龄/身份/区/小传/特质覆盖/亲属）
  events: OutageEventSpec[];                                         // 1–3 轮
}
```

`generateTown(spec) → ScenarioDef` 是纯函数，由 `spec.seed` 决定。`normalizeSpec` 负责夹取值域、补齐必需设施，并在人手撑不起岗位时削减设施，每一处调整都写进 warnings。模板规则全写在代码里：

- **地图**：沿用经典的“河分南北”骨架。
  - 两条主街，每 16 列一条纵路；纵路过河处是桥。
  - 四排地块，门一律朝南开向人行道。
  - 建筑按类型取固定尺寸，从左到右装箱；装不下就加宽地图。
  - 开放空间挂公告栏，第一个广场放喷泉。
  - 树、花、路灯、长椅用哈希稀疏撒点。
- **人口**：
  - 按年龄结构抽户型（独居、合租、夫妻、两代、三代、老两口、老人与成年子女）。
  - 按设施岗位分配身份（每类地点有固定编制）；剩下的成年人分为在家接单、照护、待业、学生、退休。
  - 特质 = 文化均值 + 身份/年龄修正 + 正态噪声；习惯由媒介比例排序后分配。
  - 外观、姓名（按年代的名字库，全镇不重名）、小传和口语风格都由模板生成。
- **关系**：朋友按同质性（年龄接近、同区、同爱好地点）抽样；跨户亲属由老人与年龄相差 20–40 岁的成年人配对。
- **经典底座**：
  - `base: 'classic'` 使用 v0 的手工小镇，只接受修饰：
    - 文化均值平移；
    - 媒介比例重新分配；
    - 公告栏个数；
    - 增加朋友；
    - 按姓名改具名人物的特质、习惯和小传；
    - 事件剧本。
  - 默认规格生成的场景与 v0 的 town30 逐字段相等（有测试）。
- **预设**：
  - 经典河岸小镇（30 人）；
  - 老城区（40 人，年长、信官方、少推送）；
  - 年轻新区（24 人，手机依赖、爱社交、不太信官方）；
  - 大镇两轮通知（60 人，两轮停电）。

### 2.6 复盘：可观测、可回放

内核新增以下纯函数，前后端同构：

- **`ChronicleBuilder`**（章节）：逐事件喂入，产出“节拍” `Beat {seq, t, kind, title, detail?, agents, family?, ref?, weight}`。
  - 节拍种类：发布、澄清、首次接触、首次相信、四分之一/半数/四分之三相信、首次转述、谣言诞生（`fill_worst_case`）、首次变模糊、改安排、调整营业、停电与来电、措手不及、信任变化、管理员干预。
  - 两个粒度：`key` 用于章节条和报告，`feed` 用于现场。
- **`personCard(s, map, id, family, t)`**：一个人在某刻的精简画像，包括阶段、所信版本与精度、置信、改过的安排、受影响与过度调整、对政府的信任、信任变化、想法。
- **`thoughtOf`**：由状态模板化生成的一句第一人称“想法”。按键取模板，确定且离线可用。“用他的口吻说”按需调 DeepSeek 润色，校验不得超出事实，只供展示。
- **`sampleSeries`**：对事件日志重放一次，按步长采样曲线。
  - 未接触、将信将疑、不信；
  - 精确 / 下午 / 全天 / 不详；
  - 改安排、受影响；
  - 对政府信任的均值与五档分布；
  - 转述次数。

复盘工作区：

- **时间刷**：范围从开始到现在，章节即关键节拍；有对比基准，默认是首次发布前。
- **反应墙**：
  - 每人一张卡：头像、阶段色块、想法、徽章（改了安排、查证、转告 N 人、措手不及、过度调整、信任↑↓）。
  - 与基准相比有变化的卡会高亮，并列出“变了什么”。
  - 可按区、户、阶段分组。
  - 点开是人物轨迹抽屉：各章节时刻的画像、信念版本变化、决定、信任变化，以及“用他的口吻说”。
- **社会**：
  - 信念构成的堆叠面积图、对政府信任的曲线与分布；
  - 谁告诉了谁的网络图（颜色 = 版本精度，大小 = 转述次数）；
  - “社会形态变化”卡片：信任均值前后对比、信任下降或上升的关系数、信息枢纽、谣言源头、跨区传播次数；
  - v0 的漏斗、普查、后果放在这里。
- **对照**：单 seed 的分支表，以及多 seed 分布（点阵 + 中位数 + 四分位）和“相对 A 更好的 seed 比例”。
- **报告**：LLM 实验报告（见 2.8）。

### 2.7 多 seed 实验

- 实验清单升级为 `{scenario, seeds: number[1–20], provider, forkAt?, until, branches: {label, patches: EventPatch[]}}`，旧的 `{seed, provider}` 请求自动转换。
- 第一个 seed 完整落库（可以在城市里打开每个分支）；其余 seed 只在内存跑，只存指标，模型调用用合成运行 id 记账。
- 每个分支 × 每轮事件的指标：
  - 半数/八成相信用时；
  - 事件开始时的知情、精确、全天人数；
  - 改安排；
  - 措手不及的人数与分钟；
  - 过度调整；
  - 版本数；
  - 对政府信任变化的均值；
  - 信任下降的关系数；
  - 决策、回退与调用。
- 聚合：中位数、四分位、最值、均值；和参照分支（第一个）逐 seed 配对，给出“更好 / 更差 / 持平”的计数与差值中位数。
- 默认分支仍为 A–D，补丁作用于第一轮事件。

### 2.8 对话建镇与实验报告（DeepSeek Flash）

**建镇会话。** `builder_sessions` 保存规格与对话，每轮一次调用：

- 输入：系统提示（模板规则、取值域、可改字段、输出格式）+ 当前规格 + 最近 8 条对话。
- 输出：JSON `{reply, patch}`。
- 服务端的处理：
  - `patch` 只允许白名单字段；
  - 数组整体替换；
  - 再做 `normalizeSpec`，把调整写进 warnings，回复里一并说明。
- 离线时对话框不可用，模板和参数表单照常可用。
- 开始实验时，规格按内容哈希登记为场景 `sc_<hash>`。

**实验报告。** 服务端先从事件日志算出“事实表”，再交给模型写报告：

- 事实表内容：设置、关键节拍、曲线要点、漏斗与后果、信任变化、3–5 个自动挑选的个体故事、多 seed 统计。每条事实都有 id。
- 模型输出 `{title, summary, findings[{text, cites}], stories[{person, text, cites}], socialChange, caveats}`。
- 校验规则：
  - 正文里的数字必须出现在事实表里（事实表预先算好百分比）；
  - 时刻必须出现在事实表里；
  - 人名必须存在；
  - 引用必须指向事实 id；
  - 不许出现事实里没有的“全天”。
- 校验失败时带着失败原因重试一次，仍失败就回退到模板报告，并标明来源。
- 报告按事实表哈希缓存。

## 3. 验收标准

1. `pnpm check` 通过。经典场景下，v0 的浸泡、溯源、确定性、重放、分叉、隔离测试全部照常通过；默认规格生成的场景与 v0 town30 逐字段相等。
2. 生成的小镇（四个预设 + 若干随机规格）满足：任意两地门到门可达；7 日浸泡零违例；同规格同 seed 同哈希；岗位、住户、关系一致。
3. 信任演化：停电来电后，见证者的信任按表中规则变化，每次变化都有事件和原因；第二轮通知的可信度用的是更新后的信任；重放一致。
4. v0 缺口：
   - “有意但受阻”至少在一个 seed 出现，原因可读；
   - 改做不用电的事只覆盖所信时段，前后恢复原安排；
   - 后果能按停电轮次分别统计。
5. 复盘：
   - 任选一刻可看到全员反应墙，并与基准对比出变化；
   - 可看到信念构成与信任曲线、传播网络、人物轨迹；
   - 章节条的节拍可点，点击后跳到对应时刻。
6. 设计：
   - 离线时，模板 + 参数表单可以造出新小镇并开始观察；
   - 在线时，对话一轮能改规格，预览同步更新；
   - 规格越界时会被规范化，并告诉用户改了什么。
7. 实验：
   - 10 个 seed × 4 个分支（规则决策）一分钟内跑完，给出分布与配对比较；
   - 真实 Jev 跑一次多 seed 小实验，花费有记录。
8. 报告：真实 DeepSeek 生成一份运行报告和一份实验报告，都通过校验（数字、人名、时刻可在事实表里找到），离线时回退到模板报告。
9. E2E 覆盖三个工作区的主流程，截图人工检查：信息层级清楚、像素风一致、无溢出、无页面错误。

## 4. 决定记录

- **D20 工作区化的信息架构**：把“设计 / 观察 / 复盘”作为一级导航，观察工作区只保留城市 + 叙事流 + 精简人物卡，分析性内容放到复盘，开发诊断收进弹窗。否决：在 v0 布局里继续加面板，或只做折叠。
- **D21 信任由经历裁决，写成事件**：规则表 `social_v1` 的前提是真相已被看见，而且只有见证者更新。这样“社会形态变化”可审计、可重放，并能影响下一轮传播。否决：让 LLM 判断信任变化（不可审计、不确定）；也否决所有人在来电后自动得知真相（不真实，而且会抹掉谣言的长尾）。
- **D22 事件规格 → 剧本**：通知、澄清、工单、断电全部由 `OutageEventSpec` 生成，分支是对规格打补丁。经典场景的输出与 v0 逐字相同，旧测试和旧数据的语义不变。否决：继续在脚本里硬编码 N001/N002。
- **D23 规则在代码，LLM 只填规格**：生成器是确定性纯函数，模板规则（设施编制、户型、地图骨架、取值域）写在内核里。LLM 只把自然语言翻译成 `TownSpec` 补丁，服务端规范化后告诉用户改了什么。否决：让 LLM 直接写地图和人物（不可控、不可复现，也难校验）。
- **D24 经典底座只接受修饰**：手工小镇的地图、人物和关系是 v0 的验收基准，不走生成器，只允许平移文化均值、重新分配媒介、改具名人物、改剧本。否决：把 town30 也改成生成，那会让 v0 的所有结论失去参照。
- **D25 复盘计算同构在内核**：`ChronicleBuilder`、`personCard`、`thoughtOf`、`sampleSeries` 都是纯函数。前端拿历史状态就地计算反应墙；服务端重放事件日志算曲线和报告事实。否决：为每种视图各写一套服务端投影。
- **D26 想法先模板、后润色**：反应墙上的想法由状态模板生成（确定、离线可用、与事实一致）。“用他的口吻说”才调模型，经校验、只供展示。否决：墙上每张卡都调模型（慢、贵，还会与状态不一致）。
- **D27 报告以事实表为界**：报告只能复述事实表里的数和名，带引用；校验失败就回退到模板报告。否决：把事件日志直接喂给模型（超长，数字不可核对）。
- **D28 多 seed 只落第一个 seed**：其余 seed 只存指标，需要看细节时用单 seed 实验重跑（确定性保证能复现）。否决：每个 seed 都完整落库（10 seed 约 70 MB/次）。

实施中新增的决定：

- **D29 现场叙事由服务端合成并推送**：`LiveRun` 持有一个用完整历史预热的 `ChronicleBuilder`，`hello` 带最近 400 条节拍，之后增量推 `beats`（聚合节拍原地更新）。这样只有一个事实来源，重连时不用在前端补历史。否决：前端各自合成（首次连接拿不到计数所需的全部历史）。
- **D30 城市常驻、切工作区只暂停渲染**：`ObserveView` 一直挂着，离开观察时 `frameloop='never'`。切回来是瞬时的，不重建 WebGL 场景。否决：按工作区卸载城市（每次切回都要重建几百个网格与纹理）。
- **D31 0 分钟的“不便”不计**：恰好在断电那一刻结束的活动不算被打断，不足 1 分钟的影响不记 `inconvenience`。v0 会把它们计入“受影响人数”，属于虚增。此项修正会让经典场景的受影响人数略降。
- **D32 答案缓存只收通过校验的输出**：`ChatClient` 的 `accept` 由调用方给出。校验失败的答案不进缓存，下次会重新请求。否决：先缓存再校验（坏答案会被永久复用）。
- **D33 经典底座遇到改人口/设施的补丁时自动切到“模板生成”**：切换后把原因告诉用户。实测 DeepSeek 会在经典底座上给出人口补丁，回复里说“改成 40 人”，实际却没生效。否决：静默忽略补丁。
- **D34 公告栏数量受开放空间限制**：公告栏只能立在公园或广场上，规范化时封顶并说明原因。

  - 章节、想法、曲线的一致性；
  - 服务端：多 seed、建镇、复盘、报告校验与回退、独白校验。
- `pnpm e2e`：18 个 Playwright 用例通过（离线），覆盖三个工作区的主流程与重连一致性，全程无页面错误；截图已人工逐张检查。
- `pnpm typecheck`、`pnpm lint` 通过，零告警。
- 真实调用（OpenRouter）：
  - **建镇对话**：两轮都正确改了规格。例如“40 人老城区、老人多、少订推送、只贴公告栏”，以及“加一轮周六上午南区停电”。
  - **报告**：运行报告和实验报告各生成过多次，都在第一次就通过校验，每份约 $0.0003–0.0004，耗时 25–50 秒。
  - **独白**：可用；编造时刻的输出会被拒绝并回退模板。
  - **Jev 3 seed × 4 分支**：579 次决策、0 回退、73 次缓存命中，$0.021。
  - **Jev 演示运行**（跑到 D04 16:20）：54 次决策、0 回退；DeepSeek 台词 87 条，其中 2 条未通过校验、已回退模板。
- 首屏：开发环境下约 0.7 秒出第一帧；切换工作区是瞬时的（城市常驻）。v0 记录的“首屏要等几秒”没有复现。

结果观察（合成轨迹，不是现实结论）：

- **经典小镇 · 规则 · 10 个 seed**：
  - 仅网站时，半数人相信的中位数约 23 小时，加推送约 5 小时（10/10 个 seed 更快）；
  - 措手不及的中位数：仅网站 3.5 人，推送加澄清 1 人。
- **Jev 与规则对照（同 3 个 seed）**：
  - Jev 驱动的居民在 4 个分支里过度调整都更少（例如仅网站 133 分钟对 730 分钟）；
  - 加公告栏和加推送两个分支里，Jev 的传播慢 2–3 小时。
  - 方向一致，但只有 3 个 seed，不足以下结论。
- **两轮通知（大镇 60 人 · 规则 · 10 个 seed）**：
  - 第一轮不发通知时，约 11.5 人措手不及；
  - 对官方的信任：照常通知的分支 10/10 上升（中位数 +0.021），不发通知的分支 9/10 下降（中位数 −0.015）；
  - 第二轮的传播与后果在两个分支间的差异落在噪声内。在 `social_v1` 的幅度下，信任变化还不足以改变下一轮行为，信任对行为影响多大是下一步需要校准的参数。

与方案的差异：见 D29–D34（服务端推送节拍、城市常驻、0 分钟不便不计、只缓存通过校验的答案、经典底座自动切生成、公告栏受开放空间限制）。

没做 / 留下的：

- v0 就欠下的约 50 题中英对照小评测仍没做；参数敏感性分析、居民采访、邻里群聊、120 人都没做。
- 报告校验只核对数字、时刻和人名是否出自事实表。模型自己算出的数，如果恰好与事实表里的另一个数相同，会漏过去。实测报告里出现过一次正确的减法（“25% 的人用了 4 分钟”）。
- 信任规则 `social_v1` 的幅度是手设的；生成器只有“河分南北”一种骨架；事件类型只有停电。
- 离线时对话建镇不可用，只能用模板和表单。
- 旧的 schema 1 开发库已按约定删除；演示运行已在 schema 2 下重建。
